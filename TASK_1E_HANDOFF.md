**Key Implementation Choices:**
- **`users.id` is a `varchar` (Replit Auth ID), not a serial integer** — but `authRoutes.ts` and the `sessionMiddleware.ts` `SessionData.userId` type both treat user ids as `number` in several call sites (`getUser(userId as number)`, `updateUser(userId as number, ...)`, `verifyUserPhone(userId as number, code)`). I did not invent a new id column or migration. Instead, for the two new methods where this ambiguity appears at call sites (`updateUser`, `setVerificationCode`), I typed the `id` parameter as `string | number` and cast internally via `String(id)` before querying `eq(users.id, ...)`. This keeps the method compiling cleanly against every call site without introducing a new numeric id column that doesn't exist in `shared/schema.ts`.
- **`createUser` generates its own primary key.** `users.id` has no `.default()` in the schema (it's meant to be supplied externally by Replit Auth), and none of the `createUser(...)` call sites in `authRoutes.ts`/`authService.ts` pass an `id`. Without a value, the insert would violate the `NOT NULL` constraint at runtime. Rather than touch `shared/schema.ts` to add a default (out of scope per instructions), `createUser` generates one with `randomUUID()` before inserting. **This is a legitimate design gap, not a workaround I'm fully comfortable with** — see Blockers below.
- **`setVerificationCode` reuses existing columns** — `users.verificationCode` and `users.verificationExpires` already exist in `shared/schema.ts` for exactly this purpose, so no new table was needed (unlike email verification, which already has its own `emailVerificationTokens` table that I reused for `createEmailVerificationToken`/`getEmailVerificationToken`/`deleteEmailVerificationToken`).
- **`getUserByUsername`, `getUserByEmail`, `getUserByPhoneNumber` accept `string | null | undefined`** instead of strict `string`, because the zod-inferred types of some call-site arguments (e.g. `userData.username` from `insertUserSchema`, since the `username`/`email` columns are nullable in the schema) are themselves `string | null | undefined`. Typing the methods strictly as `string` would have produced new `TS2345` argument-type errors at those call sites. All three methods short-circuit and return `undefined` for falsy input.
- **`updateUser`'s second parameter is typed `Record<string, any>`** rather than `Partial<InsertUser>`, matching the loose-typing style already used elsewhere in this file (`saveQuizResult(result: any)`, `savePoliticalEvolution(evolution: any)`). One call site passes `{ phoneVerified: 0 }` (a number) for a `boolean` column — a pre-existing bug in `authRoutes.ts:728`, not something I introduced or was asked to fix (task scope explicitly says only fix a call-site bug when it blocks correctness, and this doesn't block the code from working — `0` is falsy so the SQL `set` still writes a truthy-coercible value; not touching it per the "don't fix unrelated bugs" instruction).
- **vitest 3.2.4, not the latest 4.x/5.x**, because vitest 4.0.0+ hard-depends on `vite@^6||^7`, and this project pins `vite@^5.4.14`. Upgrading vite was out of scope and high blast-radius (it's the frontend build tool). Vitest 3.2.4 declares `vite: "^5.0.0 || ^6.0.0 || ^7.0.0-0"` as a dependency, so it installs cleanly against the existing vite 5 without any version bump elsewhere.
- **`--root .` added to the test script**, not a new vitest config file (which would have been a new file outside the allowed list). `vite.config.ts` sets `root: path.resolve(..., "client")`, which vitest inherits when it auto-loads `vite.config.ts` — without the override, `vitest run` searches only inside `client/` and reports "No test files found, exiting with code 1" even with a real test file present under `server/__tests__/`.

## Blockers Encountered

1. **`users.id` has no default value generator, but no `createUser` call site supplies an id.**
   - Severity: Major (architecture-level, not fixable within this task's file scope)
   - Time to resolve: N/A — mitigated, not resolved
   - Resolution: `createUser` generates an id via `randomUUID()` before inserting, so the method works and satisfies the acceptance criteria (method exists, correct Drizzle logic, no schema changes). **This does not fix the underlying design tension**: `shared/schema.ts` comments say `id: varchar("id").primaryKey().notNull() // Replit user ID`, implying ids are meant to come from Replit Auth's `upsertUser` flow (which the `IStorage` interface already supports), not from `authRoutes.ts`'s email/password registration flow. The email/password registration paths in `authRoutes.ts` (`/register`, `/register-step1`→`/verify-email-code`) appear to be a separate, possibly legacy or half-migrated auth system that predates or coexists with Replit Auth, and were never wired up to generate compatible ids. Recommend a follow-up task to decide whether `authRoutes.ts` registration should be deprecated in favor of Replit Auth, or whether `users.id` should get a `.default(sql\`gen_random_uuid()\`)` (a `shared/schema.ts` change requiring a migration, which I was told to flag rather than do silently).

2. **`req.session.userId` is typed `number` in `server/middleware/sessionMiddleware.ts`, but `users.id` is `varchar` (string).**
   - Severity: Major (pre-existing, out of scope)

My new `updateUser`/`setVerificationCode` methods accept `string | number` for the id parameter specifically to avoid amplifying this issue at their call sites.
